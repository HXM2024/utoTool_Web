## 2. 本地已做过的优化（避免重复建设）

代码里已存在一批有效优化，后续方案应在其上叠加，不要推翻：

- 画布一次只挂载 1 个工况（`CaseFrameCanvas.vue:666-668` 注释：原 9 工况 ≈ 9 200 DOM 节点）
- 拖拽/连线 mousemove 用 `requestAnimationFrame` 合帧（`CaseFrameCanvas.vue:1615-1638、3389-3395`）
- DBC 表格选区刻意走**非响应式变量 + 直接改 class**（`DbcSignalTable.vue:516-522`，注释实测：114×16 单次整表重渲染约 240 ms）
- 对象浏览器搜索防抖 200 ms（`ObjectPanel.vue:399-417`）
- 分栏拖拽 rAF 合帧（`ResizableSplitter.vue:64-82`）
- 快捷键统一单派发器（`useShortcuts.ts:172-197`）
- `toRaw` 后再 `JSON.stringify`，减少 Proxy 取值开销（多处）

**结论：卡顿不是"完全没优化"，而是剩余的几个量级更大的热点没有被处理。**

## 3. 问题根因（按影响排序）

### P0-1　DBC 信号表：非虚拟列表 + 每次改动全表尺寸测量（最重的长任务）

**位置**
- `frontend/src/components/DbcSignalTable.vue:3-92`（`el-table` 渲染全部行）
- `DbcSignalTable.vue:227-247`（`computeAutoWidths` 逐单元格 `Range.getBoundingClientRect()`）
- `DbcSignalTable.vue:836-857`（`watch(rows)` → `repaint()` → `emitAutoWidths()`；`watch(columns, deep)`；`watch(tableHeight)`；`watch(expandedKeys)`）
- `CANView.vue:5543-5548`（`onDbcAutoWidths` 回写 `dbcAutoWidth`）
- `CANView.vue:5481-5504`（列定义随 `dbcAutoWidth` 重算 → 作为 props 传回表格）

**机制**
1. 表格用 `el-table` + `tree-props.children`，初始化时 `expandedKeys` 被设为**全部报文 id**（`DbcSignalTable.vue:279-300`），437 行全部进入 DOM；每行 16 个单元格，每格是 `div` 包装 + `span` + 6 个事件（`mousedown/mouseenter/dragover/dragleave/drop`），节点数约 2.5 万。
2. 任意一次单元格提交（`cell-commit`）都会修改 `treeData` 节点 → `dbcTableRows` 重算 → `rows` 数组换引用 → `watch(rows)` 触发 `repaint()`。
3. `repaint()` 里调用 `emitAutoWidths()` → `computeAutoWidths()` 对**全部单元格**逐个做 `Range.getBoundingClientRect()`。每读一次几何都可能触发强制同步布局，这是典型的 **layout thrashing**。作者注释给出 254×15 格"几十毫秒"量级，本项目 437 行规模会放大到**数百毫秒级单任务**。
4. 回写 `dbcAutoWidth` → `dbcOrderedColumns` 重算 → `columns` 新引用 → `watch(() => props.columns, repaint, { deep: true })` **再次 repaint + 再次全表测量**，且 `deep: true` 会递归遍历全部列对象。
5. 编辑后 `el-table` 还需 diff 全部行；`cellClassName` 每格调用一次 `changeMarkOf`（`DbcSignalTable.vue:568-583`，内部 `getNodeChangeKey` 拼字符串 + Map 查询），7 000 次/帧。

**症状对应**：双击编辑单元格后输入迟滞、点「标记测试」卡一下、拖动测试参数标签掉帧、切换可见列/展开折叠明显停顿。

### P0-2　历史遗留数据 `signalRows`：每次变更同步写 localStorage

**位置**
- `CANView.vue:4310`（`signalRows` 定义）、`4322-4326`（`watch(signalRows, ..., { deep: true })` → `JSON.stringify` + `localStorage.setItem`）
- `CANView.vue:6674-6676`（`watch(mergedDbcRaw)` → `buildSignalRowsFromRaw(raw)`，全量重建）
- `CANView.vue:7325-7341`（`checkMissingSignalAttributes` 全表遍历）

**机制**
`signalRows` 在模板中**已无任何渲染用途**（模板只用了 `signalRowCount` 一个计数），但每次 DBC 载入都会把 394+ 信号转换成扁平行对象，并在**任意深层变更**时同步序列化整表写入 `localStorage`。加载大 DBC / 限定符批量替换（`applyQualifierReplace`，`CANView.vue:8565-8581`）时，这是主线程上**一次几百 KB~MB 的 JSON 序列化 + 同步磁盘写入**，且不受帧调度约束。

**症状对应**：上传 DBC 后界面"僵住"数秒、CFG 加载后短暂无响应、`QuotaExceededError` 被静默吞掉后行为异常。

### P0-3　Function 图形编辑器：一次画布操作触发 3~5 次全图 JSON 序列化

**位置**
- `CaseFrameCanvas.vue:728-750`（`emitChange`：`JSON.stringify(toRaw(frames))` + `JSON.parse`）
- `CaseFrameCanvas.vue:642-661`（props 变化时 `JSON.stringify(v)` 两次做内容比对，不一致再深拷贝一次）
- `FunctionGraphEditor.vue:559-562`（`syncActiveGroupFrames`：`JSON.parse(JSON.stringify(frames))` 再克隆一次）
- `FunctionGraphEditor.vue:571-576`（`emitGraph`：`JSON.stringify(toRaw(graph.value))` —— **整图，含全部分组的 frames/cards/mapping**）
- `FunctionGraphEditor.vue:1428-1441`（`onGraphChange` 串联上述全部动作）

**机制**
单次"移动一张卡片 / 连一条线 / 改一个卡片名"的调用链：
```
emitChange        → stringify(frames) + parse              ①
onGraphChange     → syncActiveGroupFrames → stringify+parse ②
emitGraph         → stringify(整个 graph, 含 6 组) + parse   ③
父级 v-model 回传 → 画布 watch 内 stringify ×2 做比对        ④⑤
```
以 LRA91 配置（5.3 MB / 2 319 节点 / 6 分组）计，③ 一次就是**几十毫秒**，①~⑤ 叠加后单次交互的序列化开销可达 **60~150 ms**，直接顶穿 16.7 ms 帧预算；同时产生大量临时字符串（5 MB 级）→ GC 抖动 → 表现为"拖动卡顿、松手后要等一下才跟上"。

**额外热点**：`frameCaseRowsMap`（`FunctionGraphEditor.vue:456-468`）在每次 frames 替换后重算拓扑遍历 + 参数平铺 + 笛卡尔积；`StepEditor.vue:1429-1432/1503-1513` 每次步骤改动都 `JSON.stringify(steps+params)`。

### P0-4　Function 用例列表：模板内 O(分组 × 用例) 过滤 + 无窗口化

**位置**
- `FunctionView.vue:100-164`（`v-for group` → `v-for c in casesOfGroup(grp.id)`，第 163 行还额外再调一次 `casesOfGroup(grp.id).length`）
- `FunctionView.vue:126`（`groupCaseCount(grp.id)` 再遍历一遍）
- `FunctionView.vue:1452-1457`（两个函数都是 `testCaseList.filter(...)`）

**机制**
`casesOfGroup` / `groupCaseCount` 是**普通函数**，不是 `computed`；每次组件重渲染都会对**每个分组**重新过滤整个人 `testCaseList`。1 个分组 2 000 条用例时，一次渲染约 3 × 2 000 次比较（列表 + 计数 + 空态判断），且列表**无虚拟滚动**，2 000 个 `.case-item` 全部真实 DOM（每个含 2 个按钮、3 个事件）。
**症状对应**：展开分组 / 生成后刷新预览 / 点击用例定位时代码区明显延迟。

**位置**

### P1-1　所有 `el-tab-pane` 立即渲染（页签"没打开也全挂载"）

**位置**
- `CANView.vue:22`（`el-tabs`）+ `25 / 301 / 734 / 768 / 1230 / 1466`（6 个顶层页签，其中电压页签内还有 3 个子页签）
- 全项目 `grep` 无任何 `lazy` 用法

**机制**
Element Plus `tab-pane` 的实现为 `shouldBeRender = !props.lazy || loaded || active`（`node_modules/element-plus/es/components/tabs/src/tab-pane.vue_...mjs:28-30`）。未传 `lazy` → **全部页签内容在首次进入 CAN 模块时一次性挂载**：DBC 树/表格、DTC 卡片、Other 数十个输入卡片、3 个 ECharts 实例、配置表单同时存在。
后果：首屏挂载时间长、内存占用高、任何全局样式/尺寸变化都要对整块 1 万行模板做布局计算。

### P1-2　深层响应式大对象，且零 `shallowRef / markRaw / v-memo`

**位置**
- `CANView.vue:4680`（`const treeData = ref<any[]>([])`）
- `CANView.vue:6014-6016`（`treeData.value = JSON.parse(JSON.stringify(baseTree))`）
- 全项目 `grep`：`shallowRef|shallowReactive|markRaw|v-memo|defineAsyncComponent` **0 命中**

**机制**
赋值后，DBC 的每个报文/信号/属性节点、`testParams` 数组、`fields` 对象都变成深度 Proxy。首次创建 + 后续每次 `JSON` 深拷贝重建都会产生数千个 Proxy 及其依赖映射；任一字段写入都要走 Proxy 的 track/trigger。这类数据 90% 是只读展示，属于典型的可 `shallowRef`/`markRaw` 场景。

### P1-3　`deep: true` 监听 + 全量正则遍历

**位置**
- `CANView.vue:8480-8496`（`watch(() => store.cfgData, ..., { deep: true })` → `forceQualifierReplace()`）
- `CANView.vue:8565-8581`（`applyQualifierReplace` 深度遍历 `treeData / signalRows / dtcRaw / testParamMap / commParams / diagParams / paParams / cardConfigForm / groupCardDefs`）
- `frontend/src/stores/modules.ts:532-540`（`watch(cfgData, ..., { deep: true })` → 触发 `loadA2lFromPath` / `loadDbcFromCfgDir` 网络解析）

**机制**
`cfgData` 本身很小，但 `deep: true` 的意义是"只要嵌套字段变动就全量重跑"；一旦命中，`forceQualifierReplace` 会对**整棵 DBC 树 + 整张信号表**做深度遍历与正则替换（即便有 `includes('::')` 快速跳过，也仍有 O(节点数) 的遍历成本）。两个模块各挂一个 deep watch，互相独立触发。

## 4. 优化路径（可直接落地）

> 顺序按「收益 / 风险」比排列，每项都可在独立 PR 内验证，避免一次性重构。

### 阶段一：止血（1~3 天量级，低风险，解决 70% 体感卡顿）

**① DBC 表格：把"全表自适应测宽"改成按需 / 增量**

现状：每次数据变化测全部单元格。改为：

1. 只在**用户显式点击「自适应列宽」**、或**首次载入**时全表测一次；
2. 编辑单格后只重算该列（记录每一列的 `Map<colKey, maxWidth>`，单元格提交时用 `canvas.measureText` 计算该格文本宽度，命中缓存则跳过）；
3. `watch(() => props.columns, repaint, { deep: true })` 的 `deep` 去掉，改为比较列 key 序列（`columns.map(c => c.key + ':' + c.width).join()`），避免列对象深层遍历触发重复 repaint。

预期：单次编辑的强制布局从 ~7 000 次降到 0~1 次。

**② DBC 表格：默认折叠 + 展开节流**

- `expandedKeys` 初始改为 `[]`（只显示 43 条报文行），用户按需展开；
- 「全部展开」时先渲染骨架、`requestAnimationFrame` 分批 `setAllExpanded`，避免一次性 diff 437 行；
- 中期接入窗口化（见阶段三）。

**③ 移除 `signalRows` 的同步持久化**

- `watch(signalRows, ...)` 改为 `debounce(1000)` + `requestIdleCallback`，或直接删除（模板未消费）；
- 若确需持久化，改为**仅在保存配置时**随配置一起落盘，不再单开 localStorage 通道；
- `checkMissingSignalAttributes` 改由 `dbcTableRows` 计算，消除这份冗余数据结构与整表重建。

**④ Function 用例列表：函数改为 computed 索引**

```ts
// FunctionView.vue —— 一次分组，模板直接取用
const casesByGroup = computed(() => {
  const m = new Map<string, PreviewCase[]>()
  for (const c of testCaseList.value) {
    const k = c.group_id || ''
    const arr = m.get(k) || (m.set(k, []).get(k)!)
    arr.push(c)
  }
  return m
})
const casesOfGroup = (id: string) => casesByGroup.value.get(id) || EMPTY
const groupCaseCount = (id: string) => casesOfGroup(id).length
```
并把第 163 行的 `casesOfGroup(grp.id).length` 改为复用一个局部变量（`v-if` 与 `v-for` 共用）。

**⑤ 代码预览：先降级，再异步**

- 立即：给 `.code-body` 加 `content-visibility: auto; contain-intrinsic-size: 800px;`（屏外不排版）；
- 短期：超过阈值（如 20 000 字符）时**只高亮首屏 N 行**，滚动时分段补齐；
- 中期：`hljs.highlight` 移入 Web Worker，主线程只做 `innerHTML` 赋值；进一步改成按行渲染 + 窗口化。

**⑥ `el-tab-pane` 加 `lazy`**

```html
<!-- CANView.vue -->
<el-tab-pane name="dtc" lazy>…</el-tab-pane>
<el-tab-pane name="other" lazy>…</el-tab-pane>
<el-tab-pane name="voltage" lazy>…</el-tab-pane>
```

注意：`lazy` 只影响首次挂载时机（首次激活后常驻），配合阶段三的 `v-if` 卸载策略效果更好。ECharts 页签改为「首次激活时 `init()` + `onActivated` 时 `resize()`」。

**⑦ 分栏拖拽：只在 `mouseup` 落盘**

`useResizableSize.setSize` 内删除 `localStorage.setItem`，仅保留 `watch(size)`，并在 watch 上加 300 ms 防抖（或由 splitter 在 `onMouseUp` 调 `persist()`）。

**⑧ 画布序列化收敛**

- `emitChange` 改为「脏标记 + 80~150 ms 防抖」：连续拖拽/连线期间只更新本地 `frames`，停止操作后回写一次；
- `onGraphChange` 去掉 `syncActiveGroupFrames()` 的重复深拷贝（`g.frames` 已是新数组，直接赋值即可）；
- `emitGraph` 的整图 `JSON.stringify` 仅在**保存**时执行；交互回写只传 `{ ...graph, frames }` 的浅引用（父级做引用比对）。

预期：单次交互序列化次数 5 → 1，5 MB 配置下节省约 50~100 ms/次。

**⑨ `selectedTestParam` 去掉 O(n) 扫描**

把 `selectedTestParamKey → node` 的映射在 `treeData` 变更时**一次性建立 `Map`**（与 `signalTypeLookup` 同思路），`selectedTestParam` 改为 O(1) 查表；或让详情面板保存 `node` 引用而非 key。

**⑩ 思维导图拖动合帧**

```ts

  const n = dragNode.value; if (!n) return
```

### 阶段二：结构优化（1~2 周，中风险）

1. **`deep: true` 精确化**
   - `watch(() => store.cfgData, …)` → `watch(() => [cfg.cfg_dir, cfg.a2l_path, cfg.a2l_qualifier, cfg.cdd_path, cfg.cdd_qualifier], …)`，数组浅比较即可命中需求；`stores/modules.ts` 同步改造。
   - `forceQualifierReplace` 拆成「按结构分片 + 空闲调度」（`requestIdleCallback` 分块，每块 ≤ 8 ms），或仅对**新增/脏节点**做替换。
2. **`treeData` 分层响应式**：只读子树（`fields`、`msg`、已载入的 `testParams` 快照）用 `markRaw` / `shallowRef`；仅保留 `checked`、`testParams` 等需要变更的字段为响应式。可显著降低 Proxy 数量与 track/trigger 开销。
3. **`watch(mainDbcTree)` 的深拷贝**：改为「单一数据源」——`treeData` 直接持有 `buildDbcTreeFromRaw` 的结果，不再 `JSON.parse(JSON.stringify)`；若必须隔离，使用 `structuredClone` 并在 `requestIdleCallback` 中执行 + loading 反馈。
4. **超长文件拆分**（`CANView.vue` 10 883 行、`CaseFrameCanvas.vue` 5 596 行、`StepEditor.vue` 2 954 行）：
   按页签/面板拆为子组件，`props` 只传子集。Vue 的更新粒度是组件 + 响应式依赖，拆组件能把"任意改动 → 整块 diff"降到"改动 → 单面板 diff"。这是本项目的长期最大收益项。
5. **列表窗口化**
   - Function 用例列表：固定行高 + 窗口化（或 `el-table-v2` 的虚拟列表）；
   - DBC 表格：把 `buildDbcTableRows` 展平成 `flatRows`（已有 `flatRows` 计算）后用自研窗口容器，或用 `el-table-v2` + 自绘树形缩进列（注意 `el-table-v2` 无原生树，需自行处理展开行）。
6. **离开守卫快照比对**：改为「脏标记」——所有写入入口（`setNodeField`、复选框、参数修改、拖拽落点）统一 `dirty = true`；守卫只看标记，保存成功才做一次 `JSON.stringify` 落基线。

### 阶段三：构建与内存（与业务解耦）

1. **Element Plus 按需引入**：`unplugin-vue-components` + `ElementPlusResolver`，删除 `main.ts` 的全量 `app.use(ElementPlus)` 与全量 CSS；图标改为**按需 import**（`import { Search } from '@element-plus/icons-vue'`），删除 `main.ts:21-23` 的全量注册循环。

### 6.2 采样脚本（可加入 DEV-only 埋点）

```ts
// 长任务
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    if (e.duration > 50) console.warn('[longtask]', Math.round(e.duration), 'ms', e.name)
  }
}).observe({ entryTypes: ['longtask'] })

// 帧率（拖拽过程中调用 window.__FPS__.start() / stop()）
export function createFpsMeter() {
  let last = 0, frames = 0, worst = 0, startAt = 0, on = false
  const tick = (t: number) => {
    if (!on) return
    if (last) { const d = t - last; frames++; worst = Math.max(worst, d) }
    last = t; requestAnimationFrame(tick)
  }
  return {
    start() { on = true; frames = 0; worst = 0; last = 0; startAt = performance.now(); requestAnimationFrame(tick) },
    stop() {
      on = false
      const dur = performance.now() - startAt
      return { fps: +(frames / (dur / 1000)).toFixed(1), worstFrame: +worst.toFixed(1), frames }
    },
  }
}
```
