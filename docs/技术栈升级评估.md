# AutoTool_Web 前端技术栈升级评估

> 范围：`e:\Python\AutoTool_Web\frontend`
> 数据来源：本机 `node_modules` 实际安装版本 + `npm view` 查询的 registry 最新版本（查询时间：2026-11-03）
> 定位：**只评估技术栈升级**，不含运行时卡顿修复（那部分见《前端性能分析报告.md》）

---

## 0. 结论先行

| 判断 | 结论 |
|---|---|
| 升级能否解决卡顿 | **不能**。P0 瓶颈是 O(n) 同步布局测量 / JSON 全量序列化 / 模板内全表过滤，升级框架与构建工具对这类开销几乎无影响 |
| 升级的真实价值 | ① Electron 落后 15 个大版本，**已过官方支持窗口（安全更新缺失）**；② 构建链落后 2~3 个大版本，dev/构建效率损失明显；③ 依赖声明宽松（全 `^`）导致安装结果漂移 |
| 建议做什么 | **批次 A（补丁）+ 批次 B（构建链）立即做**；批次 C（Electron）作为独立分支立项；批次 D（框架大版本）按需推进 |
| 不建议做什么 | Vue 3.6-rc、Vite 8 + Electron 45 同时跳、TypeScript 7.0.2、Element Plus 未来 3.x |
| 收益上限（对"操作流畅度"） | 综合 **10~25%**（几乎全部来自 Electron 的 Chromium 升级）；算法级修复是 **5~10 倍**，两者不在同一量级 |

## 2. 硬约束与依赖链（决定升级顺序）

| 约束 | 实测值 | 影响 |
|---|---|---|
| Node | 24.18.0 | ✅ 满足 Vite 7/8（`^20.19 \|\| >=22.12`）、sass 1.107（`>=20.19`）、Electron 45 工具链（`>=22.12`） |
| Pinia 4 peer | `vue ^3.5.11`、`typescript >=5.6.0`、`@vue/devtools-api ^8.2.1` | 当前 TS 5.4.5 **不满足** → 必须先升 TS 再升 Pinia 4 |
| vue-router 5 peer | `vue ^3.5.34`、`vite ^7.3\|\|^8`、`pinia ^3.0.4\|\|^4.0.2` | 必须先完成 Vite 7 + Pinia 3/4 |
| vue-echarts 8 peer | `echarts ^6.0.0`、`vue ^3.3.0` | 必须与 ECharts 6 同批 |
| @vitejs/plugin-vue 6 peer | `vue ^3.2.25 \|\| ^3.6.0-rc.10`、`vite ^5\|\|^6\|\|^7\|\|^8` | 兼容 Vite 5~8，可先行 |
| element-plus peer | `vue ^3.3.7` | 对 Vue 3.5 无限制 |

**由此得到唯一可行的升级顺序：**

```
A 补丁（Vue/EP/hljs/sass）
  └─ B 构建链（TS 5.9 + vue-tsc + Vite 7 + plugin-vue 6）
        ├─ C Electron（独立分支，可与 B 并行评审，但合并需在 B 之后）
        └─ D 框架大版本（Pinia 3→4 → Router 5 / ECharts 6 + vue-echarts 8）
```

## 3. 分批升级方案

### 批次 A：安全补丁（预计 30~60 分钟，风险极低）

**目标**：把三个小版本落后补齐，顺带把 `^` 收成精确版本。

```bash
git switch -c chore/deps-patch
npm i -E vue@3.5.44 element-plus@2.14.7 @element-plus/icons-vue@2.3.2 \
         highlight.js@11.12.0 sass@1.107.1
npm run build        # 含 vue-tsc 类型检查
```

**破坏点核对**
- 均为 patch/minor，无 API 变更。
- `sass` 1.107 仍支持 `api: 'modern-compiler'`（[vite.config.ts](../frontend/vite.config.ts#L27-L33) 已使用），Legacy API 未被移除。
- EP 2.14.7 对 `el-radio*` 的 `label` 传值仍兼容。

**验证**：`npm run build` 零错误 + 5 分钟冒烟（CAN 导入 DBC、Function 打开图形配置、三包打开用例）。
**回滚**：`git revert` + `npm ci`。

---

### 批次 B：构建链升级（预计 0.5~1 天，风险低）

**目标**：Vite 5.4 → 7.3.7、`@vitejs/plugin-vue` 5 → 6、TS 5.4 → 5.9.3、`vue-tsc` 保持 2.2.12。

```bash
git switch -c chore/build-chain
npm i -E -D vite@7.3.7 @vitejs/plugin-vue@6.0.10 typescript@5.9.3 vue-tsc@2.2.12
npm run build
```

**需要改动的配置项（`vite.config.ts`）**

| 项 | 现状 | Vite 7 处理 |
|---|---|---|
| `css.preprocessorOptions.scss.api` | `'modern-compiler'` | 保留即可（Vite 6+ 已默认 modern-compiler） |
| `build.target` | 未设置（默认随版本变化） | **显式设为 `'chrome124'`**（Electron 30 的 Chromium 版本），避免升级后默认 target 变化导致产物语法超纲 |
| `server.proxy` | `'/api' → 18735` | 无变化 |
| `base: '/'` | 保持 | 无变化 |
| Node CJS API | 未使用（`type: module`） | Vite 7 移除 CJS Node API，本项目不受影响 |
| `splitVendorChunkPlugin` | 未使用 | Vite 7 已移除该 API，本项目不受影响 |

**收益**
- dev 冷启动、HMR、生产构建速度提升（经验区间：冷启动 −30~50%，构建 −20~40%，需按第 6 节实测）。
- **生产运行时零收益**：产物仍需浏览器解析执行，卡顿不变。

**风险**：低。主要风险是 `vue-tsc` 与 TS 5.9 的类型收紧导致既有类型报错（预计集中在 `any` 推断与可选链），属于一次性修复。

**不建议同批做**：Vite 8.3.5。跨两个 major 且与 Electron 升级叠加时难以定位问题，留到批次 B 稳定后再单独评估。

---

### 批次 C：Electron 升级（预计 1~3 天，风险中高，必须独立分支）

**目标**：30.5.1 → 35.7.5（第一步），稳定后再 39 / 42 / 45 逐级推进；`electron-builder` 25.1.8 → 26.18.1。

```bash
git switch -c chore/electron-35
npm i -E -D electron@35.7.5 electron-builder@26.18.1
npm run electron:build
```

**为什么值得做**
- Electron 30 已不在官方支持窗口，**没有安全更新**，这对交付给客户的桌面程序是硬风险，而不是性能问题。
- 跨 15 个 major 的 Chromium 升级，V8 / GC / 合成器改进通常带来 **10~25%** 的渲染与内存改善（需实测，不作为承诺）。

**必须逐项回归的能力（`frontend/electron/main.js`）**

| 能力 | 代码位置 | 核对点 |
|---|---|---|
| 单实例锁 | `main.js:12-25` | `requestSingleInstanceLock` 行为不变 |
| 后端进程 spawn / 端口解析 | `main.js:39-53` 及 `spawnBackend` | Node 版本随 Electron 变化，`spawn`/`execSync` 参数需实测 |
| 残留进程清理 | `main.js:66-80`（`taskkill` by port） | Windows 行为不变，但需确认权限 |
| 主窗口 `webPreferences` | `main.js:1023-1029` | `nodeIntegration:false` / `contextIsolation:true` / 自定义 CSP；新版本对 `sandbox` 默认值可能不同，**必须显式声明** |
| preload | `electron/preload.cjs` | `contextBridge` 暴露面不变 |
| 托盘 / 菜单 | `Tray`、`buildAppMenu` | 图标 `nativeImage` 路径与尺寸 |
| 自动更新 | 自研 HTTP 下载 + `execFile` 安装 | 更新包下载、校验、静默安装、覆盖安装 |
| 文件对话框 / 打开目录 | `dialog`、`shell.openPath` | 路径含中文/空间 |
| IPC 通道 | `webContents.send`、`ipcMain.handle` | 通道名与参数序列化 |
| ESM 主进程 | `"type": "module"` + `main.js` 用 `import` | 新版本 ESM 主进程支持需确认 |

**风险控制**：C 批次与 B 批次分开合并；每跳一个 Electron major 都产出一次可安装包，做一次完整装机回归（安装 → 首次启动 → 后端就绪 → 五个模块走查 → 自动更新 → 卸载）。

## 5. 预期收益（区分三类，避免误判）

| 批次 | 运行时操作流畅度 | 构建 / 启动效率 | 包体 / 内存 | 维护与安全 |
|---|---|---|---|---|
| A 补丁 | 0 | 0 | 0 | 中（bug 修复） |
| B 构建链 | **0**（产物语法不变） | **高**（dev 冷启动约 −30~50%，构建约 −20~40%） | 0 | 中 |
| C Electron | **低~中**（渲染/GC 综合 10~25%，需实测） | 0 | 安装包增大（具体增量取决于版本，需实测） | **高（30.x 已 EOL）** |
| D 框架大版本 | 0~低 | 0 | 0 | 中 |

### 必须明确的预期管理

以"双击 DBC 单元格"为例，当前主线程阻塞约 250~500 ms，其中 **90% 以上来自逐单元格 `getBoundingClientRect` 造成的强制布局**（见性能报告 P0-1）。

- 升级 Electron 后：约 **230~450 ms**（改善但仍是可感知卡顿）
- 完成算法修复后：**30~60 ms**（不可感知）

**结论：升级无法替代算法修复；两者应分开立项、分别验收。**

## 6. 验证与回滚规范（每批次强制执行）

### 6.1 验证门槛

1. `npm run build`（含 `vue-tsc`）**零错误、零新增警告**。
2. 冒烟清单（每批次必跑）：

| 模块 | 操作 |
|---|---|
| CAN | 加载配置 → 上传 DBC → 表格编辑 3 格 → 标记测试 → 生成 |
| Function | 打开图形配置 → 切换分组 → 拖动卡片 → 连线 → 保存 → 生成 |
| 三包 | 打开 DTO 列表 → 编辑 → 保存 |
| Boot / UDS | 打开页面 → 列表加载 → 保存 |
| Electron（仅 C） | 安装/覆盖安装 → 单实例 → 托盘 → 后端就绪 → 自动更新 → 卸载 |

3. 量化对照（升级前后各测 3 次取中位数）：

| 指标 | 采集方式 |
|---|---|
| `dist` 总体积、chunk 数量 | `Get-ChildItem dist\assets` |
| 应用冷启动到可交互 | `performance.mark` + 主进程日志时间戳 |
| 进入 CAN 页签耗时 | 同上 |
| 常驻内存 | 任务管理器 / `process.getProcessMemoryInfo()` |
| 单次交互长任务 | `PerformanceObserver({ entryTypes: ['longtask'] })` |

4. **判定规则**：任何一项指标回退 > 10%，该批次不合入。

### 6.2 回滚

- 每批次独立分支 + 单次提交，锁文件随提交更新；
- 回滚 = `git revert <commit>` + `npm ci`（锁文件保证还原）；
- Electron 批次额外保留**上一版可安装包**，用于现场回退。

## 9. 一句话总结

**这次卡顿不是"版本旧"造成的，升级解决的是安全支持、构建效率与可维护性；要变流畅，仍须回到性能报告里的算法级修复。建议先做 A+B（低风险、见效快、为后续铺路），C 因 EOL 安全风险单独立项，D 按需；Vue 3.6-rc / Vite 8 / TS 7 暂不碰。**
