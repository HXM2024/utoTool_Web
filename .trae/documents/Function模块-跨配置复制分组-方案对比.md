# Function 模块 —— 「跨配置/跨文件复制分组」方案对比与选型

> 本文是**讨论稿**（方案对比），不是实施计划。你选完方案与子决策后，我再出可直接落地的实施计划。

---

## 1. 需求与已确认的点

**原始需求**：把**其它配置文件里的分组**复制过来，**包含该分组的卡片库、映射表、值资源库**。

**之前已确认**：

| 决策点 | 结论 |
|---|---|
| 产物形态 | **整组复制为新分组**（工况框 + 卡片库 + 映射表 + 值资源库 一起搬） |
| 入口 | 预览页**分组右键菜单** |
| 重名 | **组名自动加后缀**，不弹窗阻断 |

**本轮新增要求**：

| 新增 | 说明 |
|---|---|
| 加「导出/导入文件」 | 分组能导出成文件、也能从文件导入（跨机器/发给同事/存档） |
| 加「反向推送」 | 把当前配置的分组**写进其它配置** |
| 推送粒度到分组 | 推送时能**选具体分组**，不是整份配置 |

## 3. 方案空间：5 个正交维度

### 维度 A：搬什么

| 选项 | 说明 | 代价 | 状态 |
|---|---|---|---|
| **A1 整组搬为新分组** | 工况框 + 3 库 一起过来 | 零重映射（组内 id 自洽） | **已选** |
| A2 只把 3 库合并进当前分组 | 不搬工况框 | 必须定义库条目冲突规则（按 `name`/`id` 跳过 / 覆盖 / 重命名），且同名不同内容的卡片会语义歧义 | 已确认不做 |
| A3 只把工况框复制进已有分组 | 编排复用、库共用 | **最复杂**：必须做 `refId` 重映射 + 把源组库卡片合并进目标组，否则引用悬空（画布上卡片名显示异常） | 建议不做 |

### 维度 B：怎么传

| 选项 | 说明 | 后端改动 | 适用 |
|---|---|---|---|
| **B1 同机直读配置** | `getConfigs` 列配置 → `getConfig` 读源 → 追加到当前 | 无 | 同一个工具里的其它配置（最常用） |
| **B2 文件** | 分组导出 `.json` / 从 `.json` 导入 | 无（纯前端）或 1 个接口（见子决策 2） | 跨机器、发给同事、存档 |
| B3 后端分组模板库 | 服务端存一份"分组模板集合"，任何配置都能导入 | 2~3 个接口 + 落盘文件 + 管理面板 | 团队共用一套标准分组、配置很多 |

B1/B2 不互斥，且**共用同一套核心复制逻辑**（只是数据来源不同）；B3 是额外机制。

### 维度 C：方向

| 选项 | 说明 | 风险 |
|---|---|---|
| **C1 拉取** | 把其它配置的分组复制到**当前配置** | 无（只改内存，等用户点保存） |
| **C2 推送** | 把当前配置选中的分组写进**其它配置** | **整份覆盖写目标配置**：若目标配置正被另一个标签页/别人改过，会覆盖对方改动 → 必须弹窗明确提示"将以当前磁盘内容为基础追加分组后整体写回" |

### 维度 D：入口与交互

| 选项 | 说明 | 代价 |
|---|---|---|
| D1 右键菜单 4 项 | 拉取 / 推送 / 导出文件 / 导入文件 各一项 | 菜单从 3 项变 7 项，偏长 |
| **D2 右键菜单 2 项（推荐）** | ①「复制 / 推送到其它配置…」（一个弹窗内切换方向，**右键的那个分组预勾选**）②「导出 / 导入分组文件…」（一个弹窗内切换方向） | 意图分组，点击最少 |
| D3 一个统一弹窗 4 tab | 单入口，tab 切换 | 多一次点击 |

### 维度 E：冲突处理

| 项 | 结论 |
|---|---|
| 分组名 | 自动加后缀：`原名` → `原名_来自<源配置>` → `…_2`、`…_3`（**已确认**） |
| 库条目 | 整组搬 → 库随组走，**不存在库条目冲突** ✓ |
| Excel 导入用例 `case_id` | 后端已全局去重，不会报错；但**复制来的那份会被自动改成 `XXX_2`**（见子决策 1） |

| | **方案 A（推荐）** 纯前端 · 双来源 | 方案 B 纯前端 · 四入口 | 方案 C 引入后端分组模板库 |

## 5. 无论选哪个方案都要定的设计点

1. **只重生成 `group.id`**，组内 frame/lane/node/edge/card id 原样保留。
   依据：组内 id 只在组内被引用 —— `lane.nodeIds`/`f.nodeIds` 指向组内 `nodes`；`edge.from|to` 是 `node:<id>` 或 `seq:<主序列id>:<槽位>`；`Card.refId` 按**本分组**的 `cards` 解析（`utils/functionGraph.ts:383-395`）。重生成这些 id 需要连带重写 `lane.nodeIds` 与 edge 键，风险高、收益零。
2. **推送写回的字段边界**：只改目标配置的 `data.graph.groups`（以及规范化后的 `data.graph`），**保持** `func_steps / test_cases / test_function / xml_content / test_case_list / 配置级 mapping·cards·value_library` 不变。注意 `data.graph.frames` 是"活动分组"的镜像，追加分组不影响 `groups[0]`，所以可原样保留；若目标配置是旧结构（无 `groups`），写回的应是 `normalizeGraph()` 迁移后的结构。
3. **推送目标不允许"新建配置"**：只允许推送到已存在的配置名（新建配置已有 ConfigToolbar 的「新建」）。
4. **推送立即写盘、拉取不写盘**：拉取只改内存（沿用"用户点保存"，与 `addCaseGroup` 一致）；推送必须立即 `saveConfig` 目标配置（因为用户点的保存保存的是当前配置）。
5. **文件格式**（建议带类型与版本，便于以后兼容）：
   ```json
   {
     "type": "autotool-function-groups",
     "version": 1,
     "exported_at": "2026-09-21T15:00:00+08:00",
     "source_config": "A47D_copy",
     "groups": [ /* CaseGroup[] 原样 */ ]
   }
   ```
   导入时校验 `type`，不匹配直接报错；`version` 大于当前已知值给出警告但仍尝试导入。
6. **旧结构/空配置兼容**：源配置无 `groups` → `normalizeGraph` 迁移成 1 个默认分组（能列出来）；源配置没有任何分组 → 弹窗提示"该配置下没有分组"、复制按钮禁用。
7. **组名后缀规则**：`原名` → 冲突则 `原名_来自<源配置>` → 再冲突 `…_2`/`…_3`；同一批多选共用同一个 `used` 集合，避免批内自撞。
